# Handoff package standard

Every Bish's build ships this package to dev, whether it's a new design or a conversion. It lives in `<build>/handoff/`. The reference example is `conversions/floor-workspace/handoff/`.

**Rules:**
- Every requirement traces to a stamped `data-spec-id`.
- The manifest is generated and never edited by hand.
- IDs are scoped `BUILD::id` and never renamed after publication.
- Any gap is written down in `decisions.md`, never left silent.

---

## 1 · `README.md`
- **Basics:** build name, version, date, role(s), surfaces and owner.
- **How to run** the prototype, and which widths to review.
- **Contents:** an index of the other eight files.
- **Production stack:** Tailwind v4 CSS-first, tw-animate-css, shadcn v4 new-york on Radix, Lucide, SVAR React Kanban and dnd-kit.

## 2 · `conversion-report.md` (conversions only)
1. Inventory of the source (pass 1)
2. What changed, in a table of original → converted, grouped by shell, gold rule, tokens and type, icons, responsive, interaction and stamping
3. Removed items, each with its reason
4. Gate summary
5. Open questions

## 3 · `requirements.md`
Start from the generated skeleton. The file has one section per **frame**, then one per **section** (S01–S99). Inside each section is a table with one row per **element family** (`btn-action-rep#{instance}` counts as one row and lists its instances).

| Column | What goes in it |
|---|---|
| ID / family | `data-spec-id`, or the family with `#{instance}` |
| Level · class | frame / section / layer / component · commit / action / nav / info |
| Purpose | Why it exists, in one sentence |
| Content & data | What it shows, and the field(s) from `data-contract.md` |
| Behaviour | Click, keyboard, drag and drop, plus what opens or changes |
| States | Default, hover, focus, disabled, selected, loading, empty, error |
| Role gating | Who sees it and who can act |
| Responsive | Its posture at ≤640 / 641–1023 / ≥1024 |
| Acceptance | A testable statement: *Given / When / Then* |

Before the tables, each section lists its layout, its scroll regions and its data states.

## 4 · `<build>.manifest.json`
Generated by **Export handoff**. It includes `build`, `version`, `generated`, `states[]`, `gates[]` (the lint result for every state × width) and `entries[]`. Each entry carries `key`, `id`, `family`, `instance`, `level`, `class`, `type`, `section`, `layer`, `frame`, `tag`, `role`, `interactive`, `guideSafe`, `label`, `states[]` and `widths[]`.

## 5 · `state-map.md`
- **State table:** every state, listing its ID, label, frame, what triggers it (a stamped ID), its exits (stamped IDs) and its Canvas artboard.
- **Transition diagram:** a Mermaid `stateDiagram-v2`.
- **Data states:** all six data states for each module.

## 6 · `component-map.md`
A table with these columns: element family → DS component (or *custom block*) → shadcn primitive → variant and props → notes. List every custom block with the reason no DS component fits. Each one is a candidate for promotion into the design system.

## 7 · `data-contract.md`
- **Entities:** each entity's fields, types, source system, and whether it's live or seeded.
- **Derived values:** timers, counts and conversion figures, with the formula for each.
- **Events and mutations:** the name, payload and side effects of each (notifications, audit log), with the UI trigger that fires it.

## 8 · `qa-gates.md`
G1–G10 from `design-conversion-process.md`. For each gate, record a result (pass, fail or n/a), the evidence, the date and the reviewer. The shrink test and the 200% zoom test are recorded per state.

## 10 · `roles-permissions.md`
This file follows `documents/roles-and-permissions.md`.
- **Roles reaching the build:** every role that can reach it, and which `NavConfig` entry gets them there.
- **Matrix A:** roles × screens / sections.
- **Matrix B:** roles × actions (`<entity>.<verb>` → access state · elements · approver · audit event).
- **Matrix C:** roles × data fields (visibility scope).
- **Approval chains and audit events.**

Every permission point traces to an element stamped `data-bos-perm`.

## 11 · Engineering set (required when the build goes to dev)
- `engineering.md`: stack, structure, layout, permissions and stamping rules, definition of done
- `types.ts.tpl`: domain types
- `api-contract.md`: endpoints, server permission enforcement, live updates, audit, errors
- `build-plan.md`: epics and tickets, each mapped to requirement rows and stamps
- `test-plan.md`: automated suites (SpecLint, axe, API permissions, visual) + Given/When/Then scenarios

The dev zip contains `handoff/` + `prototype/` + `design-system/`. Reference: `conversions/floor-workspace/`.

## 9 · `decisions.md`
- **Open questions:** each with an owner and a due date.
- **Decisions made:** each with the date and who made it.
- **Retired IDs:** each old ID with the ID that replaced it.
- **Failed gates:** each with its fix plan.
